# Native and managed deployment

The active workflow uses Node processes with native or managed PostgreSQL and Redis. Docker is not required or used by the current CI workflow. Legacy container artifacts are not part of this deployment path.

## Development

Follow WINDOWS-STARTUP.md. Complete manual packages and real service configuration, generate/validate Prisma, pass typecheck, migrate the development database and run check:services, then dev:all. The launcher does not install services or substitute mock data.

Backend packages, PostgreSQL and Redis are still unavailable in the authoring environment. The steps below are not claimed as executed.

## Build and release gates

Commit the real root lockfile generated by the user's manual workspace installation. Clean deployment/CI environments use npm ci. Do not fabricate a lockfile or bypass failing checks.

```sh
npm ci
npm run db:generate -w backend
npm run db:validate -w backend
npm run typecheck
npm run lint -w backend
npm run contracts:generate
npm run test:contracts
npm run test -w frontend
npm run test:coverage -w backend
npm run build
npm audit --audit-level=high
```

Tests/coverage require an isolated *_test database and Redis DB 15 and can delete test data. Run production migrations as a separate release task after staging acceptance, backups and review.

## Independently supervised Node processes

| Service | Working directory | Start command |
|---|---|---|
| API | repository root | npm run start -w backend |
| Worker | repository root | node backend/dist/worker.js |
| Frontend | repository root | npm run start -w frontend |

Build/generate first. Use the host's Node process supervisor, Linux systemd or an appropriate Windows service manager; dev:all is not a production supervisor. The worker also needs native ffmpeg/ffprobe for media processing. No host executable installation was performed here.

Use native or managed PostgreSQL/Redis with authentication, TLS, persistence and backups. Configure Redis noeviction for durable queue data. Review Prisma connection_limit, pool_timeout and connect_timeout against the total connection budget per replica. Redis needs the full TCP protocol, Lua, blocking commands and Pub/Sub; REST-only caches are insufficient.

Run npm run db:migrate -w backend once as the intended release task. Never use production URLs for destructive tests or migrate reset. Rehearse recovery from MIGRATION-RECOVERY.md.

## Environment separation

- API/worker API_URL is the public API origin; SITE_URL is the exact frontend origin.
- Frontend API_URL or NEXT_PUBLIC_API_URL includes /api/v1. Do not accidentally share the backend origin value with this frontend variable.
- API and worker share the intended DB, Redis, encryption key and necessary provider credentials.
- Development, staging, test and production need separate data and queues.
- Production enforces HTTPS origins, non-placeholder secrets and live social adapters.

Terminate HTTPS at the host/reverse proxy, allow Socket.IO upgrades, set trusted proxy hops and exact CORS origins, and test secure httpOnly cookies. Use /health for liveness and /ready for dependency readiness. Workers require process/queue monitoring, not an HTTP check on port 4000.

Test socket load-balancing, Redis fan-out, revocation and graceful shutdown across replicas. Request logs omit query secrets. Monitor exhausted jobs, webhook failures and money reconciliation. SMTP delivery is at least once.
